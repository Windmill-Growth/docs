## Paginate results

Cursor-based lists default to 50 results and accept at most 100 unless an endpoint states otherwise.

1. Make the first request without a cursor.
2. Read `page.nextCursor`.
3. Pass that exact value as `cursor` on the next request.
4. Keep the workspace, filters, and sort unchanged.
5. Stop when `page.nextCursor` is `null`.

Treat cursors as opaque strings. Do not decode, rebuild, or round their timestamp values. Invalid or incompatible cursors return `validation_failed`.

Some MCP tools use a ranked sample, an offset, or a bounded selection instead. Follow each tool's schema. `traxy_list_agent_candidates` uses `limit` and `offset`; `traxy_find_leads` returns a matching total and a ranked sample. Do not treat a sample as a complete export.

### Count tracked profiles and posts

`GET /customer/watchlist/profiles` accepts `entityType=PERSON` or `entityType=COMPANY`. Its `total` and `totalByEntityType` describe matches across pages. Use `sort=qualifiedLeads` to rank tracked profiles by their qualified lead count.

For `GET /customer/analytics/posts`, supplying `monitoredProfileId` adds `totals` for all matching posts from that profile. `latestPostAt` identifies its latest recorded post even when it falls outside the requested date range.

Account reports use a company UUID as `accountId` when the leads are linked to a company. Unlinked leads can retain an encoded company-name ID. Pass the returned ID unchanged when reading the account report.

## Filter lead results

Lead listing defaults to active leads. Use the documented disposition and filters for other views. A score filter narrows API-visible leads; it does not bypass qualification, deletion, blocklist, or workspace access rules.

Use lead-signal and engagement endpoints when you need the evidence behind a lead. Meeting analytics and meeting listing are separate endpoints; attendee details require contact permission.

## REST errors

REST failures use this envelope:

```json
{
  "error": {
    "code": "invalid_api_key",
    "message": "Invalid API key.",
    "status": 401,
    "request_id": "req_example"
  }
}
```

| Status | What to check |
| --- | --- |
| `400` | Input validation and supported arguments. |
| `401` | Missing, expired, revoked, or inappropriate credentials. |
| `402` | Workspace access or required capability. |
| `403` | Scope, role, consent, or allowed origin. |
| `404` | Whether the resource exists and is visible in this workspace. |
| `409` | The operation-specific conflict described by the error code. |
| `429` | Rate limiting; follow retry guidance. |
| `503` | Temporary unavailability; follow `Retry-After` when supplied. |

## MCP errors

MCP has three error layers:

- Invalid HTTP bodies or authentication can fail at the HTTP layer.
- Unknown methods, unknown tools, malformed calls, or missing scopes can return a JSON-RPC error.
- A known, authorized tool with invalid arguments returns a normal result containing `isError: true`. Read `structuredContent.error.issues` for the paths to correct.

Do not treat every HTTP success as a successful tool action. Inspect the tool result and its error flag before continuing. An ambiguous write outcome is a reason to inspect state, not blindly repeat the action.
